# OneCase 民生服务扩展方案

- 日期：2026-10-09。
- 状态：产品设计与一线假设；最小人工服务跟进原型已实现，完整 AI 提取和一线服务效果未验证，覆盖范围见 §11。
- 方向依据：本轮确定将项目扩展到失业、老年等民生服务对象；沿用工作人员操作、AI 草稿、人工确认的基本边界。
- 初版设计交付：两条服务流程、合成任务卡、验收标准与实现缺口。后续原型复用现有数据库结构增加服务 API/页面；未改变模型配置或原演示数据，见 [实现记录](../devlog/LIVELIHOOD_PROTOTYPE_2026-10-09.md)。
- 关联：[PRD 基线](./PRD.md)、[Backlog](./backlog.md)、[合成任务卡](../testing/usability/livelihood-scenario-cards.md)。本地人群事项清单 `docs/research/community-group-matters.md` 尚未入库。

## 1. 产品定位与最小验证范围

目标定位：**OneCase 是面向基层服务工作人员的民生服务 AI 工作台，帮助他们把居民表达和主动探访记录整理为待确认的需求，协调服务，并持续跟进结果。**

直接操作用户先保留社区工作人员/网格员。就业服务站工作人员、养老服务协调人员是待访谈的相关角色；不能假设所有社区都有同样的职责与服务资源。居民是服务对象和信息来源，本轮不新增居民端或要求老人使用应用。

首批设计两条链路：失业人员就业帮扶、老年人助餐与探访。困难家庭、残疾人等保留为后续候选，先用这两条链路验证共同结构。人群标签可以交叉，不作为资格认定或自动风险判断依据。

待验证的价值假设：工作人员能减少重复整理，更容易找到下一步行动和遗漏的跟进。居民获得服务、找到工作或生活情况改善属于后续真实试点结果，不能由草稿数量、状态变更或合成演示推导。

## 3. 共同工作流程与记录要求

```text
居民表达 / 工作人员主动探访记录
→ AI 整理需求、原文依据与缺失信息
→ 人工确认服务对象、需求及处理范围
→ 制定下一步行动（负责人、时间、完成条件）
→ 自行协助或转介服务机构
→ 记录接收情况、服务结果和居民反馈
→ 继续跟进 / 完成本次事项 / 安排后续服务
```

以“一位服务对象的一项可独立跟进的需求”为个人服务事项单位。一条来件可以涉及多位服务对象；同一人可以有多项需求。家庭成员之间只记录经人工核实的关系，不自动共享各自的服务记录。

| 记录项（概念字段，尚未定 API） | 最小内容 | 确认责任 |
| --- | --- | --- |
| 服务对象 | 演示用 SYN-P01 等合成编号；真实试点需另定授权和识别方式 | 工作人员确认；未知对象保持未知，不能按姓名/地址自动绑定 |
| 需求 | 服务类型、居民期望、已知限制、原文来源、缺失信息 | AI 提建议，工作人员确认；咨询可当场答复并留痕，无须强建事项 |
| 下一步行动 | 做什么、内部跟进负责人、约定时间、完成条件 | 工作人员确认；外部机构不替代内部跟进责任 |
| 转介记录 | 去向、发出时间、是否接收、反馈依据、未接收原因 | 工作人员根据真实反馈记录；系统本轮不发送消息 |
| 服务结果 | 实际提供了什么、反馈来源、尚未解决的需求、记录时间 | 区分“已推荐”“已接收”“已提供”“居民确认” |
| 后续安排 | 下一次联系/探访时间、负责人、目的 | 工作人员与服务对象确认；本轮不预设政策时限或统一探访频次 |

安全紧迫性、政策办理时限和约定回访时间分别记录。不能因“属于老年/失业人群”就自动升为 P1；没有政策来源时，时间只能写成工作人员的约定，不称为法定期限。

## 4. 流程 A：失业人员就业帮扶

**服务目标**：帮助工作人员跟踪求职需求、就业服务转介及后续障碍。首次范围包括需求整理、岗位/培训服务转介与反馈；岗位搜索、自动匹配、资格审批和补贴计算不纳入本轮。

**合成起点**：SYN-P01 表达“最近失业，想找附近白班工作，晚上要照顾母亲；想了解登记怎么办”。这是自述，失业登记情况、职业经历和政策资格均未知。

| 步骤 | 工作人员动作 | AI / 工作台的设计支持 | 进入下一步的条件 |
| --- | --- | --- | --- |
| A1 接收与整理 | 核对求职需求、工作时间限制、是否还有登记咨询 | 草稿列出原文依据和缺项；不猜年龄、参保情况或资格 | 各项需求经人工确认；仅咨询且已答复的可留痕结束 |
| A2 补充与确认 | 确认技能、可工作时间、服务意愿和本机构职责 | 生成补充问题草稿；已知信息不重复要求填写 | 信息足以确定下一步；缺项不妨碍先提供通用指引 |
| A3 制定行动 | 确认内部跟进人、就业服务去向及约定回访时间 | 展示计划和待确认项 | 负责人和下一步明确；去向未核实时记录“待核实” |
| A4 转介与接收 | 在现有渠道联系服务机构，记录其反馈 | 分别记录已发出、待接收、已接收、退回及原因 | 接收方反馈有来源；已发出时仍保留跟进动作 |
| A5 服务与反馈 | 记录岗位/培训推荐、居民是否接受及拒绝原因 | 整理反馈与下一步建议，保留来源 | 知道推荐是否符合白班、距离等限制；推荐不等于就业 |
| A6 调整计划 | 不合适、退回、无资源时调整去向或约定下一次联系 | 汇总障碍，提示缺少负责人/时间 | 新行动由人确认；失联时结果保持未确认 |
| A7 完成本次事项 | 核对约定服务是否完成、遗留需求是否有安排 | 按来源展示服务结果与收尾说明 | 人工确认完成条件；仅推送岗位、接收转介不足以记为已就业 |

结果示例：“就业服务站已提供两条岗位信息，居民反馈时间不合适，继续寻找白班岗位”；或“居民自述已入职，记录反馈日期，正式就业状态未核验”。完成一次就业指导可结束对应服务事项，长期求职目标仍可继续跟进。

异常分支：登记咨询涉及资格时，核对当地正式办事指引或交对应经办人员；无合适岗位时保留障碍和下一步；居民拒绝继续服务时记录意愿、说明和人工收尾决定，结果不能写成已就业。

## 5. 流程 B：老年人助餐与探访

**服务目标**：跟踪助餐需求是否获得响应，以及后续探访安排。首次范围包括需求确认、服务资源协调、送达反馈和探访记录；医疗诊断、护理等级认定、自动紧急调度不纳入本轮。

**合成起点**：SYN-P02 的家属表示“母亲腿脚不便，最近做饭困难，想了解能否送午餐，也希望有人定期看看”。家属代述与老人本人意愿分开记录；不推断失能等级、补贴资格或饮食要求。

| 步骤 | 工作人员动作 | AI / 工作台的设计支持 | 进入下一步的条件 |
| --- | --- | --- | --- |
| B1 整理与风险核对 | 区分助餐、探访及可能紧急的情况 | 提示原文风险线索和缺项，不作诊断 | 紧急情况先按既有应急流程处理，不等待 AI 或建案 |
| B2 确认对象与意愿 | 核对代述关系、老人意愿及联系安排 | 将“家属提出”“老人确认”“未确认”分别展示 | 日常服务实施所需意愿与安排已确认；不能把家属提议当作老人同意 |
| B3 核实服务资源 | 联系当地助餐/养老服务机构，确认覆盖、时间、费用等 | 记录信息来源、核实日期和未确认条件 | 能准确说明可提供的服务；没有依据时不承诺免费或一定可办 |
| B4 制定安排 | 确认内部跟进人、拟联系时间及分别完成的条件 | 助餐与探访分别列行动，保留共同来件来源 | 每项需求有下一步；助餐完成不自动结束探访 |
| B5 协调与实施 | 用现有渠道协调，记录接收及实际送餐/探访情况 | 区分已预约、已接收、已实施及反馈 | 有实施记录；预约不等于服务送达 |
| B6 回访与调整 | 核对是否收到、能否持续使用、是否新增困难 | 整理反馈、失败原因和待办 | 结果有来源；未收到需重新协调，联系不上仍为未确认 |
| B7 后续服务 | 与服务对象约定下一次探访或回访 | 记录负责人、时间和目的 | 完成本次探访，同时保留下次安排；持续服务不能被一次办结掩盖 |

结果示例：“服务机构确认首次送餐，老人反馈已收到；后续送餐安排已说明，下次回访时间已约定”。该记录证明本次服务送达，不证明长期照护问题已解决。

异常分支：拒绝日常服务时记录本人意愿与人工决定，不自动等同 CANCELED；资源不足时保留替代去向核实动作；失联不能记为安全已确认；发现紧急风险时先协助联系既有应急渠道，事后补录处置来源，不能以等待服务意愿确认为由延迟应急处理。

## 6. 关联、状态和收尾规则

1. **同人、同需求、同一持续事项**：身份与处理范围经人工核实后，可把后续来件关联为来源；服务对象未知时先补充，不因文字相似预选关联。
2. **不同人、同类别或同地址**：个人服务事项分别跟进；同名、同楼栋、同家庭、同一代述人都不能证明是同一服务对象。
3. **同人、不同需求**：按可独立完成的目标拆分，例如求职帮扶与失业登记咨询；不为每条聊天重复建案，也不强制把已答复咨询转成长期事项。
4. **公共问题**：多位居民反映同一公共设施问题，仍可沿用人工关联原则。个人服务事项的限制不应破坏该路径。
5. **新的服务周期**：已完成后的新需求/新一轮探访保留独立服务记录或新事项，并关联历史；旧事项确需纠正时才由人按现有状态机重新打开，不自动覆盖原结果。
6. **状态与服务步骤**：拟继续使用现有 Case 状态机；待材料、待接收、待回访等作为独立的服务步骤/等待原因。其存储方式待实现设计，不能添加第二套状态迁移校验。
7. **结果收尾**：RESOLVED/CLOSED 前检查本次目标、反馈依据与遗留行动；记录拒绝、资源不足或失联的具体结果，由人决定继续、暂缓或结束，不能统一标为成功。

原型已实现个人服务查重隔离、历史对象改绑保护、收尾拦截和新周期。仍沿用原状态迁移矩阵；个人服务新来件的对象核实与来源关联尚未开放。

## 8. 一线验证与记录方式

使用 [合成任务卡](../testing/usability/livelihood-scenario-cards.md)核对流程，具体主持与匿名记录参见[可直接使用的走查包](../testing/usability/livelihood-walkthrough-runbook.md)。先纸面了解现行做法，再按实际覆盖展示人工原型；不导入真实居民资料，不重置演示库。记录主持人补充提示，避免把被引导后的回答当作独立理解。

优先验证：

- 社区实际负责哪些步骤，转给谁，能否取得接收与结果反馈？
- 服务对象与同一持续事项现在怎样识别，哪些信息不允许进入辅助工具？
- 求职、助餐、探访是否需要分别记录，什么条件才能结束或继续？
- 最耗时的是整理、转介、回访还是重复填表，新记录能否被现有台账复用？

每次记录参与者编号、材料版本、现行步骤/工具、遗漏/误关联、主持人提示、下一步复述，以及“赞同/反对/职责不符/未知”。允许不回答；未取得一线反馈时，结果栏保持“未执行”。

评价顺序：先排查误关联、遗漏需求和错误收尾，再比较独立理解与记录负担。可记录整理用时、补录次数和有负责人/下一步的未完成事项占比；少量访谈只用于方向判断，不推出总体效率提升百分比或就业/养老成效。

若现有工具更简单、反馈无法取得，或新增记录需要多填一遍，应缩减相应流程。若主要痛点是回访，后续优先做下一行动和回访记录；若主要痛点是材料整理，优先按现有台账样表映射，不能仅按本草案排开发优先级。

## 9. 实现顺序与结构影响

| 阶段 | 交付 | 验证方式 |
| --- | --- | --- |
| 设计阶段 | 本方案、合成任务卡、PRD/Backlog/索引同步 | 文档链接、范围、原有修改保留检查 |
| 最小原型 | 已实现人工对象引用、下一步行动、转介/回访与结果记录，复用现有存储 | 业务规则回归、真实库保存/刷新、UI 链路和旧公共事项回归；见 §11 |
| 一线核对 | 基于反馈修订流程，确定分类、提取契约、来源关联与专用字段是否必要 | 逐条回应 LS-01 至 LS-12；核对当地职责与现有台账 |
| 真实试点 | 在明确授权与安全条件后验证工作人员是否少重复录入、少漏跟进 | 对照现行流程；服务结果单独记录，不用模型/技术测试代替 |

需求未来会经过 AI 提取契约、领域规则、持久化、应用服务和页面。对象关联会影响查重/确认；行动与回访会影响事项详情/工作列表；分类扩展会影响字典、提取提示和 seed。字段设计前先检查这些连带影响，采用现有模块结构，不引入通用工作流引擎、微服务或新生产依赖。

初版只改设计文档；原型后续增加页面与应用服务，复用现有 CaseAction 的版本化快照，未改 schema、既有架构文档、原演示数据或外部系统。生产鉴权、访问控制、数据留存等前置条件仍需在真实资料使用前解决。

## 11. 最小原型的实际覆盖（2026-10-09）

`/services` 支持人工创建或从已确认事项启动就业、助餐、探访计划，记录对象、意愿、负责人、下一步、转介、服务反馈，并保留历史。独立演示与验证结果见 [实现记录](../devlog/LIVELIHOOD_PROTOTYPE_2026-10-09.md)。

| 标准 | 本轮覆盖 | 未覆盖部分 |
| --- | --- | --- |
| LS-01 | 可人工为不同对象/需求分别创建计划，原文成为新事项来源 | 自动多对象提取/拆分未扩展或评估 |
| LS-02 | 对象/意愿未知可保存；普通服务实施与收尾有确认门禁 | 政策资格不建自动判断能力；当地指引待核实 |
| LS-03 | 同一计划内人工追加进展与回访历史 | 新来件与个人服务的 CaseSource 关联暂未开放 |
| LS-04 | 个人服务退出公共查重池，旧关联接口拦截，已核实对象不可改绑 | 实际身份识别、家庭授权关系未建立 |
| LS-05 | 可分别建三类服务计划；旧“已答复”出口保留 | 具体办事分类、咨询与服务的最佳拆分待一线核对 |
| LS-06～LS-08 | 分别记录转介/接收/退回/实际服务/结果/失联/拒绝，包含后续时间与收尾门禁 | 真实资源、接收反馈与结果通过人工记录，未接外部系统 |
| LS-09 | 界面提醒先线下应急，人工路径不依赖模型 | 未做应急调度或真实应急测试 |
| LS-10 | 服务计划人工创建与跟进不调用模型，旧人工兜底保留 | 就业/养老分类、提示词和真实提取质量未扩展或评估 |
| LS-11 | 探访确认需后续时间；新周期独立事项关联历史并清空结果/意愿确认 | 当地频次和实际连续服务效果未验证 |
| LS-12 | 原状态 API 对个人服务执行结果/反馈依据检查 | 目标是否真正达成仍依赖人工核对与试点证据 |

## 12. 待办与回访视图（2026-10-10）

用户选择该方向后，`/services` 复用现有字段提供负责人筛选和列表；随后任务复核补充待接续入口。点击事项进入原计划/进展表单。这里的负责人是人工填写文本，不是账号权限或“我的待办”。

| 规则 | 展示方式 |
| --- | --- |
| 有 followUpAt | 以回访约定为当前联系时间，优先于计划 nextActionAt；显示时间来源 |
| 无 followUpAt | 使用计划安排；缺少或异常时间标为“时间待核对”，不静默丢弃 |
| 未收尾且到期、今日稍后、时间待核对 | 默认“待联系”；先排待核对，再排到期与今日稍后，时间从早到晚 |
| 未收尾且下一本地午夜及以后 | “未来安排”；按浏览器本机时区计算日期，时间从早到晚 |
| RESOLVED / CLOSED / CANCELED | 在“全部事项”保留历史，不因旧计划时间变成活动事项的过期待办 |
| 已完成/关闭，有明确后续约定且无同对象同服务的关联新周期 | “待接续”另列历史安排；按时间排序，不改变历史状态。取消或只有旧计划日期不提示 |
| 人工开启新周期 | 先预填原 followUpAt，请人核对；没有回访约定才默认明天。保存后建立关联并消除旧接续提示，重新确认本轮意愿及结果 |
| 调整已存在的回访约定 | 在原进展表单选择“记录回访 / 继续跟进”并填写时间；单独改计划时间不覆盖已保存回访 |

列表保留各个独立事项、下一行动、转介/结果状态与最近记录；UNKNOWN 不推断为失联，转介/退回不显示为成功。刷新列表只重新读取列表，不覆盖右侧未保存的编辑；本机每分钟重算时间分组，不自动联系、发通知或新建周期。详情中的历史探访仍由人开启新周期。

六条任务复核发现接续入口及新周期日期问题，后续修正见 [接续修正记录](../devlog/LIVELIHOOD_TASK_REVIEW_2026-10-10.md)。明确周期关联才消除提示，不用同对象、同负责人或相近日期猜测；已有后续事项也不代表实际服务成功。

结构经过现有服务 GET API → 新的纯展示派生函数 → 原服务页；写入仍走既有表单与版本校验，没有新增 API、状态机、数据表或依赖。六条合成检查不能证明减少漏跟进或真实就业/养老效果，详情见 [实现记录](../devlog/LIVELIHOOD_FOLLOW_UP_2026-10-10.md)。
