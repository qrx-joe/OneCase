# OneCase 演示与答辩准备

这份文案已同步 2026-09-05 StepFun Provider 接入的代码、测试与本地运行事实。已选用的 v2 PPTX/PDF 仍是此前导出版本，发送前需按新版讲稿重新核对并导出；v1 不再更新。本轮闭环审查没有新增外部模型调用或录制演示。

## 演示前

- 使用合成数据，不放真实居民的姓名、电话、住址或聊天记录。
- 启动后先查看 `/api/intakes/capabilities`，确认实际生效的 provider 与 model。2026-09-05 当前本地服务返回 `stepfun / step-1o-turbo-vision`，但能力接口只检查装配，不会验证模型是否支持视觉，现场仍要用合成图片试跑。
- 开场明确说当前是真实 StepFun 还是 Mock。Mock 是按规则返回结果的测试模式，只能演示文字操作流程，不能证明模型准确率，也不能识别图片。
- 检查演示数据库和候选事项。旧脚本的固定结果不一定还在，不要直接执行会清空数据的 `db:reset`。
- 文字作为主线。当前已有一条合成图片 Intake 经 StepFun 到达 Review 的运行记录；现场仍须重新用合成图片核对实际输出，未完成就只展示选择、预览、上传、刷新恢复及转人工。语音暂未支持，微信尚未接入。
- 如果准备备用录屏，从实际运行中录制，并注明版本、日期、模型模式及数据为合成示例。
- 带好笔记本和电源，提前试一次外接屏幕。完整讲述控制在 12 分钟以内，另练习 5 分钟问答。

## 两分钟演示

示例输入：

> 王主任，我们三栋二单元那个灯又坏了，我妈昨天晚上回来差点摔倒。另外楼下垃圾今天也没人清。

这是合成示例，不是真实居民留言。

| 操作                   | 可以这样讲                                                                   |
| ---------------------- | ---------------------------------------------------------------------------- |
| 打开首页，进入新建反馈 | 首页数字来自演示数据库，不是社区使用成绩。                                   |
| 粘贴文字，开始整理     | 这条消息同时说了照明和清运两个问题，需要分开处理。                           |
| 检查草稿和相似事项     | 先看拆分是否正确，信息有错就修改。现在还没有生成正式事项。                   |
| 分别选择关联或新建     | 如果照明已有记录，就关联过去；清运没有对应记录，就新建。选择以实际候选为准。 |
| 打开事项详情           | 看新增的反馈来源和处理记录，再看首页统计如何变化。                           |

旧 seed 以 CASE-018 为照明关联对象，CASE-011 用来对比不同单元。候选、顺序和状态以现场输出为准，不强行把结果讲成预设答案。候选分数只用于排序，不是重复概率。

如需展示状态变更，按页面允许的顺序操作。例如 OPEN 不能直接转 RESOLVED，需要先进入处理中。实际结果不符合预期时，说明问题，切换备用演示，不把尚未发生的操作说成已经完成。

## 常见问题

### 图片能做什么？

可以选取、拖入或粘贴一张 JPG、PNG、WebP 图片，最大 10 MB；先本地预览，也能补充文字。点击整理后图片会保存，失败后可以刷新恢复并对照原图手动创建事项。

Qwen、OpenAI、StepFun 的图片消息链路已经接通。2026-09-05 当前本地服务为 `stepfun / step-1o-turbo-vision`；一条带单张合成图片的 Intake 已真实到达 Review，数据库记录 Analysis `COMPLETED`、耗时 3449ms，并生成 1 条 Issue。这只证明当次正常链路可用，没有代表性样本集、准确率或稳定性结论。本轮闭环审查没有新增模型调用。现场必须先确认实际 provider/model 并用合成图片试跑；未完成就只展示上传、恢复和转人工。不能把上传成功、请求已发出、能力接口返回或模拟响应测试说成真实识别成功。语音入口已禁用，不现场尝试录音。

### 为什么不用聊天机器人加表格？

如果只是偶尔整理几段文字，那样可能就够了。OneCase 多做的是后面的记录工作：把几件事分开、核对是否重复、保留反馈来源，再跟进处理状态。社区是否真的需要这些功能，还要结合实际流程判断。

### AI 做了什么？

AI 把居民反馈整理成结构化草稿。Qwen、OpenAI、StepFun 的文字和图片消息适配已经接通，也保留了只用于文字流程的 Mock。代码和单元测试能证明装配、请求契约、Schema 校验、审计及失败处理；当前还有一条 StepFun 合成图片 Intake 从上传到 Review 的运行记录。真实模型能整理得多准，仍需要用代表性样本单独测。

### AI 会直接创建或合并事项吗？

不会。正常草稿检查流程中，人要选择新建、关联或拒绝。关联是在已有事项上增加反馈来源，不是自动把两个已有事项合成一个。候选也可能不对，所以仍要人工核对。

### 查重用向量检索吗？

目前没有。现在根据标题词汇、地点、类别和时间排序，最多列出三个候选及依据。是否需要 Embedding，要看后续样本效果。

### AI 失败后怎么办？

原始反馈会保留，可以重试；符合状态条件时，也能手动创建事项。默认情况下，StepFun 配置或调用失败会如实记为失败，不会静默伪装成 Mock 成功。只有 `DEMO_MODE=true` 和 `AI_ALLOW_MOCK_FALLBACK=true` 同时开启，配置失败才允许降级为 Mock，审计记录也会写成 `mock / mock-v1`。现场如果启用这个 fallback，要直接说明“真实模型不可用，已切到 Mock”；此时只演示文字流程，图片转人工。已经成功拆成多个草稿的反馈，需要继续逐项检查，不能直接绕过确认流程。演示前还要实际检查一次失败场景。

### 一个人怎么继续做？

设计、开发和测试目前由我负责。下一步先找一个具体流程试用，不急着扩功能。社区业务、安全、采购和长期运维，还需要对应的人和资源参与，这些合作目前不能当作已经具备。

### 有客户吗？能省多少时间？

目前没有可展示的客户或合作数据，也没有真实社区的提效测量。接下来想用同一批授权、脱敏的反馈，对比两种整理方式的耗时和错误情况。测试通过数不能代替这些结果。

### 能直接给社区用吗？

现在只适合用合成数据演示。真实试点前，还要补认证权限、组织数据隔离、访问频率限制和待确认草稿列表。已有长度校验和带 ID 的页面恢复，但这不等于安全和草稿管理都做完了。

### 准备怎么收费？

目前考虑部署配置费和持续运维费，还没有验证。需要先了解谁使用、谁有预算、怎么采购，以及维护成本。试用是否有价值，决定了收费方案能否继续讨论。

### 项目贡献和开源部分怎么区分？

OneCase 由参赛者独立开发，使用 AI 编程工具辅助写代码和测试。产品设计、业务规则、代码检查和最终验收由开发者负责，框架和第三方组件注明来源。主要许可证已列在 PPT 中。

项目尚未公开发布，这一点已由本人确认；商业化状态不能据此推断。赛事资格如有疑问，需要向主办方确认。发布状态不再写入展示页。
