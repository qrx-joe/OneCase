## 三、它们没能替本项目回答的问题

| 找过什么 | 本轮结论 | 可推出/不可推出 |
|---|---|---|
| 可直接套用的中国社区就业/养老完整开源闭环 | 尚未找到同时满足源码、许可、责任接收和本地使用证据的候选 | 不能推出“无人涉足”或“做不到” |
| 外部机构是否真的接收/履约 | Primero 有系统内机制；其他候选多为内部代记/配置或未核验 | 不把内部状态等同外部承诺；协议、渠道和人仍必需 |
| 当地工作人员最重的负担 | 外部框架与实施说明不能测量本地负担 | 没有依据区分“没顾上做”与“做不到”，不创造市场空白结论 |
| 一次完成能否覆盖持续帮扶 | 服务路径/活动/时间线证据支持区分过程与结果 | 可提出设计模式，不能证明居民已经受益 |

## 四、下一步最小验证方案（待决定，未执行）

建议使用既有合成卡，不运行陌生外部系统、不用真实居民资料。若选择待办方向，先设计六条合成记录：到期就业联系、转介等待、退回补充、探访后下一次联系、失联重联、已收尾历史。

完成标准：

1. 同一合成对象可有就业、助餐、探访不同需求；列表不因对象相同合并事项。
2. 可看到有效联系时间、负责人、下一动作与等待原因；未来、到期及收尾记录显示规则明确，已关闭的旧周期不变成过期待办。
3. followUpAt 与 nextActionAt 谁决定当前行动需要明确规则；不简单按日期求最小值，避免把已过去的计划时间反复显示为待办。
4. 已发出/退回/失联不会被展示为本次服务成功；内部代记接收明确给出反馈依据。
5. 日期未知或异常明确显示待核实；探访完成后仍可看到约定下一次联系或新周期。
6. 合成走查能检验误解、遗漏和操作逻辑；不能填入真实完成率、时间收益或一线满意度。

本轮交付研究文档，不创建实验结果。只有用户决定下一阶段范围后，才新建有假设、输入、做法、结果及取舍影响的实验记录。
