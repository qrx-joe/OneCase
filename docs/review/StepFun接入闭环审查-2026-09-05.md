# StepFun 接入闭环审查（2026-09-05）

## 结论

StepFun 的单张图片正常路径已经形成可核验闭环：图片上传并保存后，经实际生效的 `stepfun / step-1o-turbo-vision` 分析，结构化结果写入 Analysis 和 Issue，页面进入 Review 等待人工确认。当前运行记录中，Intake 为 `ANALYZED`，Analysis 为 `COMPLETED`，耗时 3449ms，并持久化 1 条 Issue。

这不是完整的生产闭环，也不是图片识别质量验收。异常写库恢复、E2E 环境隔离、视觉能力判断和实际 provider/model 的页面可见性仍有缺口。当前只有单张合成图片的正常路径证据，没有代表性图片集、准确率、稳定性、真实社区数据或现场网络条件下的验证。

## 已闭环的正常路径

1. `apps/web/src/lib/ai-provider.ts` 解析 `AI_PROVIDER=stepfun` 及独立 Key/Model，并在明确的 Demo 双开关下才允许配置失败降级 Mock。
2. `packages/ai/src/provider-factory.ts` 创建 `StepFunProvider`；`packages/ai/src/stepfun-provider.ts` 复用 OpenAI 兼容协议发送文字与 `image_url` 消息。
3. `POST /api/intakes/[id]/analyze` 读取已保存 Attachment，调用 Provider，并取得实际生效的 provider/model。
4. 成功事务将 Intake 更新为 `ANALYZED`，将 Analysis 写为 `COMPLETED`，再批量创建 Issue。
5. Review 页面读取 Issue，允许人工编辑并选择新建、关联或不建事项；AI 不直接完成业务处置。

当前本地运行证据：

- `GET /api/intakes/capabilities` 返回 `provider=stepfun`、`model=step-1o-turbo-vision`、`imageProviderConfigured=true`。
- Intake `cmtn9d60y0001dh595ievwt5o` 的来源为图片，含 1 个 Attachment，状态为 `ANALYZED`，Review 中有 1 个待人工处置的 Issue。
- 对应 Analysis 为 `COMPLETED`，审计字段为 `provider=stepfun`、`modelVersion=step-1o-turbo-vision`、`latencyMs=3449`、`errorMessage=null`。

这些证据能证明“当次请求贯通并持久化到 Review”，不能证明 Issue 内容正确，也不能把能力接口、合成请求或接口契约测试说成模型识别效果。

## 未闭环问题

### P1：成功结果最终写库失败时可能长时间停在 `ANALYZING`

证据：`apps/web/src/app/api/intakes/[id]/analyze/route.ts` 的 Provider 调用错误在 129—205 行有独立恢复逻辑；成功后的状态更新、Analysis upsert 和 Issue createMany 位于 208—260 行的事务中。该事务异常会落入 282—287 行的通用 500，但没有立即把本批次 Intake 恢复为 `PENDING`。

影响：数据库瞬时故障、约束错误或 Issue 写入失败时，用户只能等待陈旧分析超时恢复，现场会表现为持续“分析中”。

建议：为成功收尾事务增加同批次 CAS 恢复和失败审计；加入故障注入测试，覆盖 Analysis/Issue 写入失败且 Intake 可立即重试。

### P1：Playwright E2E 会复用真实服务并重置数据库

证据：`apps/web/playwright.config.ts` 配置 `reuseExistingServer: true`；`apps/web/tests/e2e/reset.ts` 在每个 spec 前执行 `db:reset`。当前 3000 端口服务使用 StepFun，而 golden path 断言依赖固定 Mock 输出。

影响：直接运行完整 E2E 可能清空当前演示数据库、产生真实或付费请求，并因真实模型输出变化而不稳定。

建议：给 E2E 使用独立数据库和独立端口，启动时强制 `AI_PROVIDER=mock`，不复用日常开发服务；真实 Provider 只保留明确标记、默认不执行的冒烟测试。

### P2：图片能力接口可能误报

证据：`apps/web/src/app/api/intakes/capabilities/route.ts` 以 `provider !== 'mock'` 计算 `imageProviderConfigured`，没有检查具体模型是否支持视觉。

影响：若 StepFun、Qwen 或 OpenAI 配成纯文本模型，前端仍会显示图片 Provider 已配置，现场可能把装配成功误解为视觉可用。

建议：维护明确的模型能力配置，或把字段改名为“非 Mock Provider 已装配”；真正的视觉能力仍通过合成图片冒烟确认。

### P2：Review 页面看不到实际 provider/model 与 fallback

证据：分析 API 的成功响应包含 provider，但 Review 页面只保存 `analysisId` 和 `issues`；model 仅在数据库审计字段中，页面没有展示实际模式。

影响：操作者无法在关键结果页直接确认是真实 StepFun 还是 Mock fallback，现场说明依赖额外接口或数据库查询。

建议：成功响应同时返回 model 和 degraded/fallback 状态，并在 Review 显示只读运行标识。

### P2：StepFun 专属失败链路覆盖不足

证据：StepFun Provider 有模拟成功响应和共享装配测试；失败恢复主要由 Qwen/OpenAI 或通用路径覆盖，缺少一次从 StepFun HTTP 失败到 Intake `PENDING`、Analysis `FAILED`、provider/model 审计的专属集成测试。

影响：协议兼容不等于错误体、超时和审计行为完全一致，StepFun 特有失败格式仍可能暴露遗漏。

建议：使用本地模拟 HTTP 服务或请求拦截增加 StepFun 401、429、5xx、超时及非法 Schema 覆盖，不调用真实服务。

## Demo 与现场如实说明

- 开场先读取能力接口，明确本次实际 provider/model；同时说明该接口只证明装配，不证明视觉能力。
- 用合成图片做现场预检。成功时只说“这一次图片从上传经 StepFun 到达 Review，仍由人确认”，不要说“已经验证识别准确”。
- Mock 只演示文字工作流，不能识别图片。真实 Provider 失败时保留原始输入，转文字或人工创建；不得把 Mock 固定输出说成真实识别。
- 只有 `DEMO_MODE=true` 与 `AI_ALLOW_MOCK_FALLBACK=true` 同时开启时，配置失败才允许降级 Mock；运行时请求失败不会自动伪装成 Mock 成功。
- 现场仍需确认网络、额度、模型可用性、能力接口返回值、合成图片输出和 Review 中实际结果。
