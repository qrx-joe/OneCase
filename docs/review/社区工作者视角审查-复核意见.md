# OneCase《社区工作者视角的问题与解决方案》复核意见

- 复核日期：2026-09-01
- 复核对象：[社区工作者视角-问题与解决方案.md](./社区工作者视角-问题与解决方案.md)
- 复核方式：只读核对 README、PRD、TASK、Prisma Schema、核心页面、API 与领域代码
- 复核目标：判断问题是否成立、代码证据是否准确、方案是否适合进入开发路线图

## 一、总体结论

这份审查抓住了 OneCase 从比赛 Demo 走向真实社区试点时最重要的几类问题，尤其是：

1. 产品入口与社区工作人员的移动工作现场错位；
2. 无法承载真实居民数据；
3. 不导入、不导出时容易成为现有系统之外的“第四本账”；
4. 人工确认成本可能抵消 AI 整理带来的收益；
5. 持续跟进、催办、回访和迎检可能比“记录”更接近真实痛点。

问题方向总体正确，但这份文档目前更适合作为“产品化问题池”，不宜直接作为开发路线图。主要原因是：

- 部分代码事实描述不准确；
- 一些业务判断尚无真实用户和计时数据支撑；
- 若干方案低估了认证、权限、数据治理和导入导出的复杂度；
- 第一阶段真实影子测试与第二阶段才建设合规能力之间存在矛盾；
- 对未校准重复候选使用默认关联，会引入自动化偏见并破坏原有信任设计。

综合判断：约 70% 的问题判断可以保留，但应修正事实、区分证据等级，并重新排列实施顺序。

## 二、基本成立、建议保留的问题

### 1. P2：当前不能承载真实居民数据

该判断成立。

当前项目明确处于合成数据演示状态，没有生产级认证、访问控制和数据留存机制。居民原文和图片还可能被发送给配置的模型服务。因此，“请勿录入真实居民隐私”不是普通提示，而是当前系统的真实使用边界。

但解决方案不能简化为“换国内模型端点 + 加密字段”。进入真实试点至少还需要：

- 服务端认证与 session；
- 组织和对象级授权；
- 服务端注入操作人身份，不能信任前端提交的 `userId`；
- 数据最小化、留存、删除和脱敏导出规则；
- 模型输入、日志、备份和附件的完整数据边界；
- 密钥管理、访问审计和异常处理；
- 与试点单位确认部署、授权和数据处理责任。

### 2. P3：可能成为“第四本账”

该判断成立，并且可能比部分 AI 能力更影响实际采用。

OneCase 当前不替代 12345 或既有网格化平台。如果无法导入历史台账，也不能把处理结果导出为社区已有材料，工作人员就需要重复录入。

建议优先验证一个确定格式的 Excel 导入和导出闭环，而不是一开始承诺兼容所有社区台账。导出模板应由真实样表决定，不能仅凭推测定义字段。

### 3. P4：确认成本可能超过整理成本

该问题成立，但文档中的“手写台账 30 秒”目前没有证据，应标记为待验证假设。

需要测量的不只是页面操作时间，还包括：

- 从微信或电话接收信息到开始登记的切换时间；
- 整理事实和补充缺失信息的时间；
- 查找是否重复的时间；
- 跟进、催办、回访和办结材料整理时间；
- 误建、漏建和错关联产生的返工时间。

### 4. P5：语音缺位

“语音暂未支持”是准确事实，老人语音和电话也是值得验证的场景。

但语音转写不应在未经验证时直接列为 P0。它会增加音频上传、模型出域、识别纠错、方言适配、成本和留存风险。应先确认语音是否真是目标社区最高频且最费时的输入，再决定采用第三方 ASR、私有化 ASR 或人工转写辅助。

### 5. P6：重复检测存在冷启动和地点标准化问题

该判断基本成立。

当前重复检测仍是未校准启发式，Embedding 尚未接入。历史导入、社区地点字典和真实 Duplicate Gold Dataset 都是查重能力成立的前提。

需要注意：历史数据导入不只是把旧 Case 灌入数据库。还要处理字段映射、地点别名、类别映射、重复记录、无效状态、时间格式、错误报告和可回滚性。

### 6. P7、P8：台账字段和类别不足

现有 Case 确实缺少联系方式、责任主体、时限和处理后附件等真实台账常见信息；Seed 类别也只有 5 个。

但最终字段和类别不能仅由产品团队推测。应先收集目标社区的真实脱敏台账样表和类别字典，再决定：

- 哪些字段属于 Case；
- 哪些属于居民或联系人；
- 哪些属于办理动作和回访记录；
- 哪些属于可配置字典；
- 哪些敏感字段需要独立权限和留存策略。

### 7. P9、P10：催办缺失和工程术语

这两项基本成立，而且适合做低风险、可快速验证的改进。

“新建 Intake”“AI 事件化”“Case”等词应改成社区工作人员能直接理解的业务语言。催办、逾期、待回访和长时间无进展事项，也比装饰性的通知铃铛更有实际意义。

## 三、需要修正的事实描述

### 1. “无移动端适配”不准确

代码中已经存在 1024px 和 768px 响应式规则：

- `intake-grid`、`review-layout` 等布局会在窄屏变为单列；
- 768px 以下侧栏和顶栏搜索会隐藏；
- 内容区边距会缩小。

真正的问题是：

- 手机端隐藏侧栏后，没有底部导航或其他替代入口；
- 表格没有降级为适合手机的信息卡片；
- 关键操作的触控尺寸、键盘遮挡、滚动和真机流程尚未验证。

建议把原文改为：

> 已有基础响应式样式，但手机端导航缺失，表格和关键操作尚未完成移动优先设计，当前不能视为移动端可用。

### 2. “已有 userId，只缺登录和界面”不准确

当前 Schema 的真实情况是：

- 有 `User` 模型；
- `Case` 有 `assigneeId`，但没有 `createdById`；
- `CaseAction` 有可空的 `userId`；
- `Intake` 没有创建人字段；
- Review 页面提交的是固定字符串 `demo-user`。

因此认证并非只缺一个登录页面。还需要调整数据模型、API 身份来源、组织范围校验、授权策略和审计链路。

### 3. “没有搜索”不完整

“全部事项”页面已经有客户端本地搜索，可按标题、编号、地点和类别过滤。

失效的是 `AppLayout` 顶栏中的全局搜索框。最小处理可以是：

1. 删除顶栏死搜索；或
2. 将顶栏查询跳转并传给已有事项搜索；

不一定需要立即新建服务端搜索 API。

### 4. “不建案轻路径”已有部分实现

Review 已有 `REJECTED` 决策，界面显示为“跳过”，并且会留痕。

真正缺少的是业务语义，而不是底层能力。建议把模糊的“跳过”改成更清楚的业务选项，例如：

- 已答复，无需跟进；
- 仅记录，不形成事项；
- 无效或重复信息；
- 暂不受理，并记录原因。

## 四、原解决方案中的主要风险

### 风险 1：未校准候选不应默认关联

原文建议高分候选（如 `score > 0.85`）默认选择“关联”。当前评分明确标记为“未校准”，演示中的高分也来自合成数据编排。

即使最终仍需用户点击确认，预选关联也会产生自动化偏见，使工作人员更容易接受错误候选。这与“AI 不替人做主”和“重复检测只辅助判断”的信任原则相冲突。

建议：

- 没有候选时，可以测试默认“创建新事项”；
- 有候选时，保持人工主动选择；
- 只有在真实 Gold Dataset 上完成 Precision、Recall、Hard Negative 和阈值校准后，才测试推荐预选；
- 在任何阶段都不自动执行关联或合并。

### 风险 2：真实影子测试与合规建设顺序矛盾

原路线图第一阶段要求 5 位社工真实使用两周，第二阶段才建设登录、权限、加密和私有化部署。

这两者不能同时成立。合规建设前，系统仍明确禁止录入真实居民隐私。

建议区分：

- **可用性测试**：使用合成或充分脱敏材料，验证入口、理解成本、流程时间和操作错误；
- **真实影子试点**：完成最低认证、授权、部署和数据治理门槛后，才使用经授权的真实业务数据。

### 风险 3：PWA 分享路径被描述得过于确定

Web Share Target 只能在 PWA 安装并被操作系统注册后成为分享目标，且浏览器和操作系统支持并不一致。当前公开资料主要确认 Android WebAPK/ChromeOS 等场景，不能直接承诺“安卓微信长按消息即可转入”。

iOS 自动读取剪贴板也会受到 HTTPS、用户激活、权限或显式粘贴确认限制，不能设计成无感自动读取。

因此应先做目标设备、微信版本和安装路径的真机 Spike，再决定是否采用。相关资料：

- [MDN：share_target](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/share_target)
- [web.dev：PWA OS integration](https://web.dev/learn/pwa/os-integration)
- [MDN：Clipboard API](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API)

### 风险 4：当前不应删除隐私遮挡提示

在认证、权限、留存和模型数据边界尚未解决时，删除“遮挡姓名、电话等非必要信息”提示并鼓励录入联系方式，会扩大当前系统的隐私风险。

建议：

- Demo 阶段继续要求脱敏；
- 试点阶段把联系方式设计为独立受控字段；
- 明确访问角色、使用目的、留存期限、删除方式和日志脱敏；
- 完成相关能力后，再替换当前 Demo 风险提示。

### 风险 5：阶段 1 范围过大

原路线图希望在 2–3 周内同时完成：移动端、PWA 分享、语音转写、术语、死按钮、默认决策、导入导出、字段、附件和类别扩展。

这些工作跨越 UI、领域模型、数据库、AI Provider、文件处理、权限和真实设备验证。即使能够完成代码，也很难判断最终采用率由哪项变化带来，失败时也无法定位关键假设。

## 五、建议的验证与实施路线

### 阶段 0：先验证真实问题，不扩系统

目标：确认社区工作人员最重的工作环节是什么。

工作内容：

1. 访谈或观察 5 位一线工作人员；
2. 使用脱敏样本绘制“接收—登记—处理—催办—回访—办结—迎检”流程；
3. 记录各环节耗时、切换系统次数和返工原因；
4. 收集脱敏台账模板、类别字典和地点表达；
5. 明确真实数据试点所需的单位授权和部署边界。

验证门槛：能够用证据回答“最重的是录入、查重、催办、回访还是材料整理”。

### 阶段 1：最小手机可用闭环

目标：验证 OneCase 是否能让一条脱敏居民信息更快完成整理。

建议只做：

- 补手机端导航；
- 保证输入、Review 和事项详情在手机上可操作；
- 中文化核心术语；
- 删除或接通死按钮；
- 将“跳过”改成明确业务出口；
- 没有重复候选时，测试默认“创建新事项”；
- 记录完成时间、返回修改次数和放弃率。

暂不同时建设 ASR、企微、私有化模型和完整数据库迁移。

验证门槛：使用合成或脱敏材料时，关键任务时间和错误率优于现有原型，并且工作人员能独立理解操作。

### 阶段 2：验证台账兼容价值

目标：判断导入导出能否避免双重录入。

建议实现：

- 一个经过真实样表确认的 Excel 导入模板；
- 导入预览、错误报告、重复处理和可回滚机制；
- 一个按真实迎检或月报格式定义的 Excel 导出；
- 打印视图；
- 初版地点和类别映射。

验证门槛：工作人员无需再次手工整理同一批数据，且导出结果可直接或经少量修改用于现有流程。

### 阶段 3：真实试点门票

目标：允许一个社区在明确授权下使用真实数据。

至少包括：

- 认证和 session；
- 组织与对象级授权；
- 创建人、负责人和操作人模型；
- 服务端身份注入；
- 访问审计；
- 敏感数据、附件和日志治理；
- 留存、删除和脱敏导出；
- 符合试点要求的模型与存储部署方案。

验证门槛：通过试点单位的数据和安全要求审查，才能开始真实数据影子运行。

### 阶段 4：基于真实数据校准 AI 与自动化

目标：证明查重、地点标准化、语音等能力能带来净收益。

按证据逐步建设：

- 地点字典和别名；
- 社区类别字典；
- 历史数据清洗；
- Duplicate Gold Dataset；
- Embedding、阈值和 Hard Negative 校准；
- 催办规则；
- 语音转写；
- 企微或上级系统集成。

每项能力都应单独验证，不因“看起来完整”一次性全部投入。

## 六、建议采用的证据分层

后续文档应明确区分以下事实：

| 证据等级 | 可以证明 | 不能证明 |
|---|---|---|
| 代码检查 | 某字段、页面或逻辑存在 | 一线人员会使用、业务有效 |
| 本地测试 | 逻辑和流程按测试样例运行 | 真实设备、真实数据和真实组织适用 |
| 合成数据演示 | 产品概念可表达 | 查重准确率、效率提升、生产安全 |
| 脱敏可用性测试 | 用户能否理解和完成任务 | 真实业务持续采用、合规就绪 |
| 授权影子试点 | 真实流程中的效率、错误和留存 | 大规模部署效果 |
| 持续生产使用 | 特定组织中的实际价值 | 自动推广到其他社区仍然有效 |

任何“节省时间”“一多半诉求”“高相似”“比手写快”等结论，都应注明来自哪一层证据。

## 七、最终建议

保留原审查中的问题意识，尤其是“入口、台账兼容、确认成本、催办和持续使用”五条主线；但不要直接按原路线图进入开发。

当前最合理的下一阶段是：

1. 用脱敏材料恢复真实工作流和耗时基线；
2. 修复手机端关键路径与业务语言；
3. 验证一个确定格式的台账导入导出；
4. 价值成立后补齐真实试点所需的认证、授权和数据治理；
5. 最后用真实数据校准查重、语音和集成能力。

核心原则不变：AI 只提供草稿和候选，不自动创建业务事实、不自动关联、不自动合并，也不以未校准分数替代工作人员判断。
