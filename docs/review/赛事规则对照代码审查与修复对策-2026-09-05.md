## 3. 问题与修复对策

### R1：状态更新的乐观锁未落实到数据库写入

**代码位置**：`apps/web/src/app/api/cases/[id]/status/route.ts`，版本检查约第 58 行，数据库更新约第 85 行。

**问题与触发条件**

接口先在事务外查询事项并比较 `expectedVersion`，进入事务后却只按 `id` 更新。两个请求同时读到同一版本时，都可能通过检查。后提交的请求会覆盖前一次更新，状态合法性检查和审计仍使用旧状态。

**复现证据**

使用实际接口和状态机代码，配合受控 Prisma 替身，让两个请求同时读到 `OPEN / version=1`，分别请求 `CANCELED` 与 `IN_PROGRESS`。两个响应均为 200，最终版本为 3，两条审计的 `fromValue` 都是 `OPEN`。这证明并发保护逻辑存在缺口；本次没有进行真实 SQLite 并发压测。

**修复对策**

1. 在同一事务中，以 `id + expectedVersion` 作为条件执行原子更新；必要时同时匹配读取到的状态。
2. 使用条件更新的影响行数判断是否抢占成功。影响 0 行时抛出冲突，回滚事务并返回 409。
3. 只有成功更新的请求才能写状态审计；状态变更和审计必须同事务提交。
4. 返回更新后的真实版本；前端收到冲突后刷新事项并提示用户重新确认。

**验收标准**

- 在独立测试库构造两个同版本并发更新，只允许一个成功，另一个返回 409。
- 版本只增加 1，成功审计只有 1 条。
- 原有合法迁移、非法迁移和顺序提交测试继续通过。
- 非法迁移或版本冲突均不改变事项和审计。

**结构影响**：主要修改状态 API 的持久化逻辑，沿用 domain 状态机，无需改变公共请求字段。

### R2：AI 请求超时未覆盖响应正文

**代码位置**：`packages/ai/src/openai-compatible.ts`，约第 85—130 行。

**问题与触发条件**

`fetch()` 收到响应头后即完成，其后的 `finally` 清除了超时计时器。后续 `res.json()` 和错误响应的 `res.text()` 不再受该计时器保护。若模型服务发出响应头后迟迟不结束正文，请求可能持续等待，前端停留在“AI 整理中”。

**复现证据**

本地 HTTP 服务立即返回响应头，延迟约 250 ms 返回正文。实际 Provider 函数配置 `timeoutMs=50`、`maxRetries=0`，仍在约 311 ms 后成功返回。复现没有使用真实模型或凭据。

**修复对策**

1. 将响应状态检查及正文读取纳入同一超时保护范围，正文读取完成或失败后再清除计时器。
2. 区分正文解析错误与请求中止；不要把超时中止吞掉后归类为“无内容”。
3. 成功响应和错误响应都应受限，超时后统一转换为可识别的 Provider 错误。
4. 保持有限重试，明确总等待预算包含多次尝试；前端显示的等待和恢复提示应与实际预算一致。

**验收标准**

- 分别测试响应头迟到、成功正文迟到、错误正文迟到、正文永不结束。
- 每次尝试在配置超时附近结束，允许合理调度误差；总尝试次数不超过配置值。
- 正常响应和 Schema 校验不受影响。
- 分析接口在超时后进入失败恢复路径，用户可以重试或使用符合条件的人工兜底。

**结构影响**：主要修改共享 Provider 请求层，Qwen、OpenAI、StepFun 一并受益；回归其共用行为。

### R3：中文地址造成错误的“地点一致”提示

**代码位置**：`apps/web/src/lib/text-similarity.ts` 约第 55 行；`apps/web/src/lib/duplicate-service.ts` 约第 86—100 行。

**问题与触发条件**

`buildingUnitMatch()` 只通过 `/\d+/g` 提取阿拉伯数字。任一地址没有匹配数字时直接返回 `true`，随后依靠字符相似度判断地点。中文数字表示的不同单元可能得到“地点一致”。

**复现证据**

用实际评分代码，将草稿地点“三栋二单元”与候选“三栋一单元”比较，标题、类别相同，候选创建时间为当前时间。结果得分约 **0.96**，匹配依据包含“地点一致”，未提示“位置不同”。

虽然系统不自动合并，这一错误提示仍会误导工作人员，削弱查重机制的可信度。

**修复对策**

1. 在地址比较层归一化常见中文数字、阿拉伯数字和全角数字，保留原始地址用于展示和审计。
2. 按楼栋、单元、楼层等带语义的字段提取信息，避免直接比较地址中的所有数字序列。
3. 对明确冲突的楼栋或单元返回“位置不同”，不增加地点匹配分。
4. 地址不完整时标记为无法确认或地点相近，不因缺少数字而得出“地点一致”。

**验收标准**

- “三栋一单元”与“三栋二单元”必须标记位置不同。
- “三栋二单元”与“3栋2单元”可以识别为相同结构化位置。
- 覆盖“十二栋”、全角数字、缺失单元和含门牌号的地址。
- 地点冲突时不再展示“地点一致”；无足够地址信息时保持不确定性。
- 原有 Top 3 排序和人工确认流程继续通过。

**结构影响**：修改地址解析与查重依据生成，保留现有人工选择机制，无需引入 Embedding 或新依赖。

### R4：AI 成功后落库失败，入口状态无法及时恢复

**代码位置**：`apps/web/src/app/api/intakes/[id]/analyze/route.ts` 约第 209 行与第 282 行；接管阈值定义于 `apps/web/src/lib/intake-status.ts`。

**问题与触发条件**

AI 成功后，更新 Intake、写入 Analysis 和 Issues 的事务若失败，会整体回滚。此前抢占分析权的 `ANALYZING` 状态仍然保留，外层仅返回 500，没有专门收尾。当前重试和人工兜底需等待 10 分钟的过期接管阈值。

**证据边界**：由实际异常路径静态确认，尚未注入数据库故障复现。

**修复对策**

1. 为成功落库事务增加专门的异常捕获，区分模型失败和结果保存失败。
2. 数据库仍可访问时，使用 `id + ANALYZING + claimedAt` 校验本批次所有权，再恢复为可重试状态。
3. 记录失败阶段，避免把模型已经成功的情况误报为识别失败。
4. 如果数据库持续不可用，明确告知保存未完成；保留过期接管机制，不能承诺一定即时恢复。
5. 保留当前批次保护，不允许迟到请求回退已被新分析或人工处理接管的状态。

**验收标准**

- 注入一次性 Issues 写入失败，确认没有部分草稿残留，数据库恢复后无需等待 10 分钟即可重试。
- 重试成功后只有一组有效草稿，不重复创建业务事项。
- 模拟新批次接管或人工确认，旧请求异常收尾不得覆盖新状态。
- 持续数据库故障时返回明确错误，不伪报成功或可即时恢复。

**结构影响**：分析 API 的事务与恢复逻辑，必要时补充错误响应字段；不改变“AI 只生成草稿”的业务边界。

### R5：Eval 无法评估当前 StepFun 模型

**代码位置**：`packages/ai/__tests__/eval.test.ts`，约第 11、28、80 行。

**问题与触发条件**

只有 `EVAL_PROVIDER=qwen` 且存在对应密钥时才会选择真实模型。设置 `stepfun` 或其他值会运行 Mock；Qwen 缺少密钥时也会落入 Mock。真实模型分支的汇总断言为 `passed >= 0`，质量不达标仍可使测试通过。

因此现有“20 条 Eval 全通过”只证明 Mock 可执行规格通过，不能代表 StepFun 的提取质量。

**修复对策**

1. 使用统一 Provider 工厂选择评估模型；显式指定不支持的 Provider 或缺少必要配置时直接报错。
2. 明确区分离线 Mock 回归、请求协议测试和真实模型效果评估。
3. 真实评估输出实际 provider/model、Prompt/Schema 版本、样本版本、各项指标和失败样例。
4. 分别记录拆分漏项、类别与地点错误、未知信息处理、失败率和时延；图片样本单独统计。
5. 在与业务使用者确定标准后增加可选验收门禁，探索性评估与正式验收不要共用“始终通过”的汇总判断。

**验收标准**

- StepFun 配置确实调用 StepFun；非法配置或缺少密钥明确失败，不能悄悄变为 Mock。
- 真实效果报告不会把协议测试通过率当成识别准确率。
- 样本包含多事项、中文地址差异、信息缺失、图文冲突与不可识别图片。
- 正式验收达到预先约定标准才算通过，未达到时列出偏差。
- 真实模型调用需另行安排，使用获准的数据和调用预算；本报告不代表已完成真实评估。

**结构影响**：主要修改评估工具与报告方式，复用 Provider 工厂，不改变业务请求流程。

**验收标准**：未登录访问被拒绝；跨组织读写被拒绝；伪造请求身份不能改变审计归属。完成前继续使用合成数据演示。
