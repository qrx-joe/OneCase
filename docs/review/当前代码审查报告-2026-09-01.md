- 审查日期：2026-09-01
- 审查版本：`4070238`（`main`）
- 审查范围：阶段 1 手机可用闭环、Review 决策、查重、全局搜索、通知汇总、移动端事项列表，以及相关 API 和测试
- 审查方式：代码只读检查、TypeScript 类型检查、单元测试、定向 Playwright E2E

## 一、总体结论

当前阶段 1 代码整体可运行，类型检查、141 项单元测试及两条定向 E2E 均通过，工作区保持干净。

本次审查仍发现 4 个明确问题：

1. 首次查重失败会被误判为“没有候选”，并自动预选新建事项；
2. 已在事项页时再次使用全局搜索，URL 会变化但列表可能仍使用旧关键词；
3. 通知角标会重复计算同时满足状态条件和停滞条件的同一事项；
4. 手机端事项表格虽然变成卡片，但字段标签消失，信息含义依赖用户猜测。

其中第 1 项会破坏“查重失败不得默认建案”的产品红线，建议在真人可用性测试前优先修复。其余 3 项属于阶段 1 的功能完整性和可理解性问题，也应在 Gate 1 前处理。

## 二、审查发现

### [P1] 首次查重失败被误判为“无候选”，并默认新建

#### 代码证据

Review 页面首次加载分析结果后，会并行请求每个 Issue 的重复候选：

- 文件：`apps/web/src/app/intake/[id]/review/page.tsx`
- 关键位置：第 83–119 行

当前逻辑在以下两种情况下都会返回空数组：

```ts
return dupRes.ok && dupData.data?.candidates ? dupData.data.candidates : []
```

```ts
catch {
  return [] // Duplicate 检索失败不阻塞 Review
}
```

随后，所有结果会直接进入默认决策函数：

```ts
setDecisions((prev) =>
  prefillCreateForEmptyCandidates(prev, allCandidates, { skip: editedIdx })
)
```

#### 实际影响

当前代码无法区分：

```text
查重成功，确实没有候选
```

与：

```text
查重接口返回 500／网络请求失败
```

因此真实执行路径可能变成：

```text
查重服务故障
→ 返回空数组
→ 被解释为没有相似事项
→ 自动选择“新建事项”
→ 用户可直接确认
→ 产生重复事项
```

这与阶段完成记录中“检索失败不预填”的声明不一致，也削弱了 Duplicate 失败时的保守边界。

#### 测试缺口

现有 `default-create.spec.ts` 只覆盖“接口成功且候选为空”，没有覆盖首次 `/api/duplicates/find` 返回 500 或网络异常。

`duplicate-refresh.spec.ts` 中存在刷新阶段的失败测试，但不能覆盖首次页面加载分支。

#### 建议修复

让每个首次查询返回带状态的结果，而不是只返回数组：

```ts
type DuplicateResult = {
  ok: boolean
  candidates: DuplicateCandidate[]
}
```

处理时：

1. 只有 `ok === true && candidates.length === 0` 才允许预填 `CREATE_CASE`；
2. 失败项写入 `dupErrors`；
3. 失败项加入默认决策函数的 `skip`；
4. UI 显示“候选检索失败，请人工选择”；
5. 增加首次请求 500 和网络失败 E2E。

#### 验收标准

- 首次查重成功、候选为空：默认选择新建；
- 首次查重成功、有候选：不预选；
- 首次查重失败：不预选，显示失败提示；
- 用户已有决策：任何迟到响应都不能覆盖；
- `LINK_EXISTING` 在任何情况下都不能自动预选。

### [P2] 已在事项页时，全局搜索参数更新但列表可能不更新

#### 代码证据

事项列表页通过 `useState` 读取一次 URL 查询参数：

- 文件：`apps/web/src/app/cases/page.tsx`
- 关键位置：第 51 行

```ts
const [searchQuery, setSearchQuery] = useState(searchParams.get('q') || '')
```

顶栏搜索使用：

```ts
router.push(`/cases?q=${encodeURIComponent(q)}`)
```

当用户从其他页面进入 `/cases?q=关键词` 时，组件首次挂载能够读取参数。但如果用户已经位于 `/cases`，再次从顶栏搜索另一个关键词，路由只更新查询参数，`CasesView` 不一定重新挂载，`searchQuery` 会继续保留旧值。

#### 实际影响

用户可能看到：

- 浏览器 URL 已更新为新的 `?q=`；
- 顶栏搜索已经执行；
- 事项列表仍按旧关键词过滤；
- 页面内搜索框仍显示旧值。

这会让刚接通的全局搜索再次表现为“死按钮”。

#### 建议修复

优先选择以下一种状态模型：

1. 以 URL `q` 为唯一查询来源，不维护重复的本地查询状态；或
2. 使用 `useEffect` 监听 `searchParams` 中的 `q`，并同步 `searchQuery`。

同时应明确页面内输入框的行为：

- 是实时本地过滤；还是
- 输入后更新 URL，再由 URL 驱动列表。

避免顶栏搜索和页面搜索维护两套不同状态。

#### 验收标准

增加一条 E2E：

1. 进入 `/cases`；
2. 顶栏搜索关键词 A；
3. 不离开事项页，再搜索关键词 B；
4. URL、页面搜索框和列表结果都应同步为 B；
5. 浏览器前进、后退时查询结果也应恢复。

### [P2] 通知角标重复计算同一个事项

#### 代码证据

`AppLayout` 将三个非互斥集合直接相加：

- 文件：`apps/web/src/components/AppLayout.tsx`
- 关键位置：第 89–96 行

```ts
const notifRows = summary
  ? [
      { label: '待处理', value: summary.open, href: '/cases?status=OPEN' },
      { label: '处理中', value: summary.inProgress, href: '/cases?status=IN_PROGRESS' },
      { label: '超 7 天未更新', value: summary.stalled, href: '/cases?stalled=7' },
    ].filter((row) => row.value > 0)
  : []

const notifTotal = notifRows.reduce((sum, row) => sum + row.value, 0)
```

但 `stalled` 可以与 `open` 或 `inProgress` 重叠。

例如：

```text
事项 A：OPEN，且 10 天未更新
```

当前计算结果为：

```text
待处理：1
超 7 天未更新：1
角标：2
```

实际只有一个事项。

#### 实际影响

- 角标数字可能大于实际事项数；
- `aria-label` 会读成“共 2 项”，对无障碍用户形成错误信息；
- 用户可能误判工作量；
- 单元测试验证了重叠计数存在，但没有验证角标语义是否正确。

#### 建议修复

先明确产品语义：

**方案 A：角标表示独立待办事项数**

- 在原始 Case 列表上按 Case 去重；
- 一个事项无论命中多少条件，角标只计 1；
- 下拉分组仍可分别显示状态和停滞数量。

**方案 B：角标表示提醒条件数**

- 保留当前求和方式；
- 将“共 N 项”改成“共 N 条提醒”；
- 明确同一事项可能产生多条提醒。

从社区工作人员的工作量认知看，更建议方案 A。

#### 验收标准

- 一个停滞的 OPEN 事项不会被角标显示为两个事项；
- 下拉分组仍能展示它同时属于“待处理”和“停滞”；
- 可见文案和 `aria-label` 使用同一统计口径。

### [P2] 手机端事项卡片缺少字段标签

#### 代码证据

移动端样式隐藏了表头，并将每个表格单元格纵向展示：

- 文件：`apps/web/src/app/globals.css`
- 关键位置：第 1693–1718 行

```css
.case-table thead {
  display: none;
}

.case-table td {
  display: block;
  padding: 3px 0;
  border-bottom: 0;
  text-align: left;
}
```

当前移动卡片实际呈现类似：

```text
CASE-018
3栋2单元楼道照明故障
公共设施
3栋2单元
P2
处理中
```

隐藏表头后，“类别、地点、优先级、状态”等标签没有替代展示。

#### 实际影响

- 用户必须依赖字段顺序猜测含义；
- `P2` 等工程编码缺少解释；
- E2E 只证明页面无横向滚动、流程能够点击，不能证明信息可理解；
- “表格卡片化”只完成了布局变化，没有完成信息结构变化。

#### 建议修复

可以采用：

**方案 A：`data-label`**

给每个 `td` 增加字段名，并在移动端通过伪元素展示。

**方案 B：独立移动端卡片组件**

将核心信息组织成：

```text
事项标题                         P2
CASE-018                         处理中

地点：3栋2单元
类别：公共设施
更新：2026-09-01
```

考虑后续还会加入负责人、时限和催办信息，更建议使用独立的语义卡片结构。

#### 验收标准

- 手机端可见“地点、类别、优先级、状态”等标签；
- 不依赖表格列顺序理解字段；
- 卡片整块可点击，同时支持键盘访问；
- E2E 不只检查横向溢出，还应断言关键标签可见。

## 三、仍未解决的真实试点阻断项

以下问题不是本轮新回归，但当前代码仍不具备真实居民数据试点条件。

### 1. 认证和对象级授权缺失

- API 没有 session；
- 通过 ID 可以直接读取 Intake 原文和附件；
- `organizationId` 可以由客户端传入；
- `resolveOrgId` 对非 `demo-org` 的值直接原样返回；
- `userId` 仍由前端提交固定字符串 `demo-user`。

因此现有 `organizationId` 过滤不能视为租户隔离。

### 2. Case 编号并发风险

`apps/web/src/lib/case-number.ts` 仍使用：

```ts
const count = await tx.case.count()
return `CASE-${String(1000 + count + 1).padStart(3, '0')}`
```

并发创建时可能生成相同编号，删除历史 Case 后也可能复用已有编号。当前唯一约束会让其中一个事务失败。

### 3. 图片存储仍只适合 Demo

- 图片完整编码为 data URL 存入 SQLite；
- 读取 Intake 时可直接返回完整图片内容；
- 暂无附件访问授权、生命周期和删除策略；
- 大图片会增加数据库、JSON 响应和内存压力。

### 4. 真实设备和真实用户证据缺失

- 移动端验证基于 Playwright Chromium 375×812；
- 未验证安卓微信内置浏览器；
- 未验证 iOS Safari／微信；
- 未执行 5 位社工脱敏可用性测试；
- 尚不能声称“手机上比手写快”。

## 五、建议修复顺序

| 顺序 | 问题 | 原因 | 建议验证 |
|---:|---|---|---|
| 1 | 首次查重失败误触发默认新建 | 可能制造重复事项，违反产品红线 | 首次 500／网络失败 E2E |
| 2 | 事项页全局搜索状态不同步 | 用户直接感知为搜索失效 | 连续两次搜索 + 前进后退 E2E |
| 3 | 通知角标重复计数 | 错报工作量，统计口径不一致 | 重叠事项单测 + UI 断言 |
| 4 | 移动卡片缺少字段标签 | 影响一线用户理解，当前 E2E 未覆盖 | 标签可见性和键盘访问 E2E |

完成以上修复后，再进入 5 位社工的脱敏可用性测试。认证、对象级授权、附件治理和编号并发问题应作为真实数据试点前的独立 Gate，不应与普通 UI 优化混在一起。
