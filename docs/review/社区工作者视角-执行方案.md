# OneCase 问题整改执行方案

- **版本**: v1（2026-09-01）
- **依据**: [问题与解决方案 v2](./社区工作者视角-问题与解决方案.md)、[复核意见](./社区工作者视角审查-复核意见.md)、PRD/TASK/现有代码
- **性质**: 按阶段 0–4 推进的执行计划；每阶段末有验证门槛（Gate），**不通过则不进入下一阶段**
- **执行者假设**: 1 人独立开发 + 阶段 0 需接触 5 位一线社工

---

## 〇、全局红线（所有任务默认遵守，违反即返工）

| # | 红线 | 来源 |
|---|---|---|
| R1 | AI 只生成草稿和候选；创建/关联/关闭/跳过全部人工触发；**任何阶段不自动关联、不自动合并** | PRD 核心规则 |
| R2 | **未校准评分不得预选"关联"**；预选/推荐仅在 Gold Dataset 校准后测试 | 复核风险 1 |
| R3 | 合规门票（阶段 3）完成前，系统继续显示"请勿录入真实居民隐私"，**不删除遮挡提示**，测试一律用合成/脱敏数据 | 复核风险 2/4 |
| R4 | 未知字段保持 null/UNKNOWN，不猜测；Dashboard 只统计已确认 Case | README 关键约束 |
| R5 | 每项改动保持现有测试绿：`pnpm --filter @onecase/domain test`、`@onecase/ai test`、`@onecase/web test + typecheck`、黄金链路 E2E | 工程基线 |
| R6 | 每阶段一个分支，阶段末合并；不跨阶段顺手扩 scope | TASK 工作方式 |

## 一、阶段总览与门槛

| 阶段 | 主题 | 预估投入 | 覆盖问题 | Gate（通过才进下一阶段） |
|---|---|---|---|---|
| 0 | 验证真实问题，不写业务代码 | 1 周（含约访） | 全部问题的证据基线 | 能用数据回答"最重的是录入/查重/催办/回访/材料整理"，拿到 ≥2 份脱敏台账样表 |
| 1 | 最小手机可用闭环（合成/脱敏材料） | 1.5–2 周 | P1(移动) P4 P9 P10 | 3–5 位社工用手机完成关键任务，时间与错误率优于现有原型，能独立理解操作 |
| 2 | 台账导入导出闭环 | 2–3 周 | P3 P6(导入) P7(字段) P8 | 同批脱敏数据经导入→使用→导出，无需二次手工整理，导出可直接用于现有流程 |
| 3 | 真实试点门票（认证/授权/治理/部署） | 3–4 周 | P2 | 通过试点单位数据与安全审查，获得书面授权 |
| 4 | 基于真实数据校准 AI 与自动化 | 持续，逐项立项 | P1(企微/分享) P5 P6(校准) P9(深化) | 每项能力单独验证净收益后才投入下一项 |

> 阶段 1 与阶段 2 可部分并行（导入导出的模板设计依赖阶段 0 样表，可先行做 exceljs 技术验证）；阶段 3、4 严格串行在 Gate 之后。

## 二、阶段 0：验证真实问题（访谈与基线）

**目标**: 把 v2 文档里所有"待验证假设"变成有证据的结论。不写业务代码。

| 任务 | 内容 | 产出物 |
|---|---|---|
| S0-T1 访谈提纲 | 10–15 个问题：消息来源渠道占比（微信文字/语音/电话/上门）、每类频次、当前记录方式、查重怎么做、催办靠什么、迎检材料怎么交、返工场景 | `docs/research/interview-outline.md` |
| S0-T2 流程计时 | 用脱敏样本请社工现场走一遍"接收—登记—处理—催办—回访—办结—迎检"，逐环节计时并记录切换系统次数 | `docs/research/time-baseline.xlsx`（分环节耗时表） |
| S0-T3 样表收集 | 收集 ≥2 份脱敏台账样表/迎检材料模板、社区类别字典（若有）、地点叫法清单（栋/单元/公共区域俗称） | `docs/research/ledger-samples/`（脱敏后入库） |
| S0-T4 语音占比确认 | **必答题**：语音/电话是否最高频且最费时？转写由谁做、多久？ | 结论写入访谈记录，决定 S4-T4 是否立项 |
| S0-T5 授权边界备忘 | 与候选试点单位口头确认：部署位置、谁能授权、数据能否出域、模型能否私有化 | `docs/research/pilot-boundary.md` |

**Gate 0 判定**（写进 `docs/research/stage0-conclusion.md`）：
1. 最重环节排名（录入/查重/催办/回访/材料整理）+ 数据支撑；
2. 台账样表字段清单 → 反哺 S2-T1 字段映射与 S3-T1 模型设计；
3. 语音结论（立项/不立项 ASR）；
4. 若结论推翻 v2 假设（如"催办才是最重"），回退修订问题文档后再排阶段 1 范围。

## 三、阶段 1：最小手机可用闭环

**目标**: 一条脱敏居民信息在手机上完成"录入 → AI 草稿 → 决策 → 建案"比现状更快更好懂。**本阶段不做**：ASR、企微、PWA 分享、私有化、PostgreSQL 迁移、字段加密。

### S1-T1 手机端底部导航（P1）

- **改动**: `apps/web/src/components/AppLayout.tsx` 新增底部 Tab（今日工作 / 居民来件 / 全部事项），≤768px 显示底部 Tab（现有媒体查询已隐藏侧栏，直接补替代入口）；`globals.css` 增加样式；内容区预留底部安全距离。
- **验收**: 375×812 视口下三个一级页面均可通过底部 Tab 到达；无侧栏时无死路。

### S1-T2 关键路径移动可操作（P1）

- **改动**:
  - `intake/page.tsx`：输入页单列、textarea/按钮触控目标 ≥44px、处理浮层在小屏不遮挡操作栏；
  - `intake/[id]/review/page.tsx`：草稿卡与候选面板改为纵向堆叠（现有 `review-layout` 窄屏单列基础上微调间距）；
  - `page.tsx` / `cases/page.tsx`：`case-table` 在 ≤768px 降级为卡片列表（复用现有行数据，改渲染组件）。
- **验收（新增 E2E）**: `tests/e2e/mobile-golden-path.spec.ts`，以 375×812 viewport 跑通黄金链路（粘贴 → 分析 → 关联+新建 → 详情改状态），全部按钮可点、无横向滚动。
- **不做**: 真机适配声明以 Chrome DevTools + 至少 1 台安卓真机抽查为准，不追求 iOS 深度优化。

### S1-T3 术语中文化（P10，半天快赢）

- **改动清单**（仅 UI 文案与文档，**API 路径与内部字段名不动**）：
  - `AppLayout.tsx:37` "新建 Intake" → "居民来件"；`page.tsx:147` "+ 新建 Intake" → "+ 居民来件"
  - `intake/page.tsx` 步骤面板 "AI 事件化" → "AI 草拟"
  - 状态标签 "等待外部" → "等待物业/街道"（`page.tsx` / `cases` 页 STATUS_BADGES）
  - `cases/[id]/page.tsx:281` "用户 cXyZ…" → "待分派"（登录前统一显示待分派，S3-T1 后显示真实姓名）
  - 同步 README 演示脚本中的按钮名称
- **验收**: 全局搜索 UI 层无 "Intake/事件化" 英文术语残留（`grep` 检查 components 与 app 目录的中文案）；现有 E2E 断言若依赖旧文案同步更新。

### S1-T4 死按钮修复（P9，1 天快赢）

- **顶栏搜索**（`AppLayout.tsx:110-121`）：二选一——
  - 方案 a（推荐）：回车跳转 `/cases?q=<词>`，`cases/page.tsx` 初始化时读 `searchParams` 填入已有本地搜索；
  - 方案 b：直接删除顶栏搜索框。
- **通知铃铛**（`AppLayout.tsx:117`）：接现有数据即可，**不需要新字段**——点击展开下拉，显示"待处理 N · 处理中 N · 超过 7 天未更新 M"（由 `/api/cases` 数据按 status+updatedAt 计算），点击条目跳转对应筛选列表。
- **验收**: 两个控件点击均有真实响应；铃铛数字与列表页一致；新增单测覆盖超期计算函数。

### S1-T5 "跳过"改为业务出口（P4）

- **改动**:
  - Schema：`IntakeIssue` 增加可空 `disposition`（枚举：ANSWERED / NOTE_ONLY / INVALID / DEFERRED）与 `dispositionNote`（`prisma migrate`，默认 null，旧数据不受影响）；
  - `contracts/schemas.ts`：confirm 请求体为每个 issue 增加可选 `disposition`；
  - `review/page.tsx:440-449`："跳过"按钮改为四选一弹层（已答复，无需跟进 / 仅记录，不形成事项 / 无效或重复信息 / 暂不受理，须填原因）；
  - 详情：`intake/[id]` 页与 Case Timeline 展示处置结果留痕。
- **验收**: E2E 新场景"一条两问题消息 → 一条建案 + 一条'仅记录'"；disposition 为空时后端拒绝（沿用现有校验风格）；domain/contracts 单测覆盖枚举校验。

### S1-T6 无候选时默认"创建"（P4，遵守 R2）

- **改动**: `review/page.tsx` 初始化 decisions 时，`candidates[i]` 为空的 issue 预填 `CREATE_CASE`，卡片显示"已默认选择新建，可更改"；**有候选的 issue 一律不预填**，LINK_EXISTING 永不预选。
- **验收**: 单测：有候选时 decisions 不含预填；E2E：单事项无候选消息可两步确认完成；README 补充说明"预选仅限无候选场景，评分未校准前不做关联推荐"。

### S1-T7 可用性测试执行（Gate 1）

- **方式**: 人工计时 + 录屏，**不建埋点系统**。用 S0-T2 同一批脱敏任务，请 3–5 位社工分别用现有原型和阶段 1 版本完成，记录：任务完成时间、返回修改次数、放弃率、术语理解（口头复述"这个系统让你做什么"）。
- **产出**: `docs/testing/stage1-usability.md`，含对比数据与失败任务归因。
- **Gate 1 判定**: 关键任务时间与错误率优于原型；社工能独立完成并复述流程。未过 → 只修归因指向的条目，不加新功能。

## 四、阶段 2：台账导入导出闭环

**目标**: 让 OneCase 不是"第四本账"。**前置**: Gate 0 拿到的真实样表。**本阶段不做**: 认证（导入导出接口挂 DEMO_MODE 保护，仅本地/演示库可用）。

### S2-T1 字段映射设计（P7 前置）

- 依据样表逐字段决定归属：Case / 联系人 / 办理动作（CaseAction）/ 可配置字典（Category、地点）/ 敏感字段（标记，留待 S3 加密）。
- **产出**: `docs/product/ledger-field-mapping.md`；若样表含"办结时限/责任单位"，则在本阶段给 Case 增加 `dueDate`、`responsibleParty`（可空列 + 导入映射 + 详情页展示），否则推迟到阶段 4 催办立项时。

### S2-T2 Excel 导入（P3/P6）

- **技术**: `exceljs`（新增依赖，需确认 License 与包体）。
- **接口**: `POST /api/admin/import/cases`，支持 `dryRun`（只校验返回预览）与 `commit`（事务写入）。
- **能力清单**: 模板列映射（按 S2-T1 文档）、类别码映射表、地点别名归一（初版人工维护的映射表即可）、错误行报告（行号+原因，可下载）、导入批次号（`importBatchId` 标记，支持按批次回滚删除）、重复检测提示（导入行 vs 库内启发式，仅提示不阻止）。
- **验收**: 用真实脱敏样表跑通 ≥100 行导入：dryRun 报告准确、commit 后 Case 可查、回滚后库还原；单测覆盖映射/别名/错误分支；E2E 一条导入→查重可见的链路。

### S2-T3 导出与打印（P3）

- **接口**: `GET /api/export/cases?month=&category=&status=&format=xlsx`，列结构按 S0 迎检样表定义；`/cases/print` 打印视图（print CSS，含编号/事项/地点/类别/状态/办结情况）。
- **验收**: 导出文件请社工人工核对"可直接或少量修改后用于现有流程"；打印视图 A4 单页排版。

### S2-T4 类别字典可配置（P8）

- 依据 S0 类别字典补全 seed；新增简单管理页 `/settings/categories`（列表 + 增改停用，挂 DEMO_MODE）。
- **验收**: 新增类别后 intake/案例页下拉与统计即生效；停用类别不出现于新建但历史数据正常显示。

**Gate 2 判定**: 一批脱敏台账完成"导入 → 日常使用 → 导出/打印"，社工确认无需二次手工整理。未过 → 修模板与映射，不进入阶段 3。

## 五、阶段 3：真实试点门票（合规与部署）

**目标**: 满足"一个社区在书面授权下使用真实数据"的最低要求。

| 任务 | 内容 | 验收 |
|---|---|---|
| S3-T1 身份模型与注入 | Schema：`Case.createdById`、`Intake.createdById` 必填（迁移为已有数据回填 demo-user）、`CaseAction.userId` 必填；删除三处硬编码 `'demo-user'`（`review/page.tsx:256`、`cases/new/page.tsx:53`、`cases/[id]/page.tsx:114`），改为服务端从 session 注入 | 所有写操作带真实操作人；跨用户操作留痕 |
| S3-T2 认证与授权 | 账号密码 + httpOnly session（自建或 next-auth，二选一后记 ADR）；登录页；每个 API 校验 session 组织与对象归属（当前仅 organizationId 过滤，README 已知限制），补 AC-11 跨组织拒绝的 E2E | 未登录访问业务 API 全部 401；跨组织 404/403 且不泄漏存在性 |
| S3-T3 数据治理 | 联系方式等敏感字段加密列（应用层 AES-GCM，密钥走环境变量）；访问审计表（谁在何时看了哪个 Case 详情）；留存/删除/脱敏导出规则文档化并实现"按事项删除" | 审计可查询；删除后原文与附件不可恢复；脱敏导出可用 |
| S3-T4 模型与存储边界 | 图片从 SQLite data URL 迁至对象存储/文件卷 + 路径引用；SQLite → PostgreSQL（`provider` 切换 + 数据迁移脚本）；模型端点改为试点单位认可方案（私有化或合规云），数据处理范围写入授权文件 | 迁移脚本可重复执行；模型调用边界经试点单位确认 |
| S3-T5 试点审查 | 与试点单位过一遍安全清单（认证/授权/加密/留存/备份/密钥/日志），签署数据授权与处理责任文件 | **Gate 3**: 审查通过 + 书面授权，才开始真实数据影子运行 |

**本阶段明确不做**: 完整 RBAC 矩阵、多租户计费、SSO——只做"单组织多角色最小集"。

## 六、阶段 4：基于真实数据校准 AI 与自动化（逐项立项，每项独立验证）

> 顺序即优先级；每项立项前先写一句话假设与验证方法，验证不过即停。

| 任务 | 假设 | 内容 | 验证 |
|---|---|---|---|
| S4-T1 地点字典与归一 | 地点归一能显著提升查重候选质量 | 社区地点树 + 别名表（栋/单元/区域），录入补全 + AI 提取后归一 | 抽样 50 条真实 intake 的地点归一准确率 |
| S4-T2 查重校准 | 校准后候选 Precision 足以测试推荐预选 | 基于真实数据建 Duplicate Gold Dataset（≥150 对，含 Hard Negative）；接入 embedding（canonical text + cosine，Schema 已有 CaseEmbedding 表）；用现有 `eval.test.ts` 框架输出 Precision/Recall/阈值 | Gold Dataset 上报告指标；**达标后才允许测试 R2 中的推荐预选** |
| S4-T3 催办规则 | 超期提醒能减少沉底 | 若 S2 未加 `dueDate` 则此刻补字段；通知中心扩展逾期/超期规则 + 首页"今日逾期" | 试点期逾期率对比 |
| S4-T4 语音转写 | （仅当 S0-T4 证实）语音是高频费时入口 | `packages/ai` 增加 `transcribe` Provider 接口（与 extract 平级，Mock 明确返回不支持）；选型按 S3 确定的数据边界（私有化 ASR 或合规云）；录音 → 转写文字进入现有文字流程 | 转写文字经人工修正后建案的时间 < 现行人工转写 |
| S4-T5 一步进入 | Share Target/剪贴板在目标设备可用 | 先真机 Spike（安卓微信 + 目标机型安装 PWA 路径），验证通过才实现 `share_target` 与粘贴询问 | 社工实际从微信带入一条消息的步骤数 ≤2 |
| S4-T6 企微入口 | 试点社区有企微组织且愿接入 | 企微自建应用接收转发消息建档（沿用 Intake 模型，sourceType=wechat） | 试点社区真实使用 ≥2 周 |
| S4-T7 上级平台上报 | 试点单位有明确对接需求 | 单向推送 API（OneCase → 上级平台工单） | 对接联调通过 |

## 七、横切要求

1. **回归策略**: 每个任务合并前跑该包单测 + `typecheck`；涉及页面流程的跑黄金链路 E2E；阶段末跑全量（含 build）。现有 76 项单测是底线，只增不减（允许随行为变化更新断言，需在提交说明中写明）。
2. **分支与回滚**: 每阶段 `stage-N` 分支，任务级 commit；导入/迁移类操作必须可回滚（批次删除 / 迁移脚本双向）。
3. **文档同步**: UI 文案变化同步 README 演示脚本；Schema 变化同步 TECH_SPEC 与 PRD 附录；每个 Gate 结束在 `docs/devlog/` 记一篇阶段结论（含未验证项，沿用 TASK.md 的 communicating 模板）。
4. **证据标注**: 新增任何"更快/更准"的说法前，先对照 v2 文档第五节证据分层表注明来源层级。
5. **范围守卫**: 每阶段开工前把"本阶段不做"清单贴进任务描述；出现新想法一律进 `docs/product/backlog.md` 排队，不顺手实现。
