# ADR-003: SQLite → PostgreSQL 迁移时机 —— 参赛阶段不迁移

**状态**: Accepted  
**日期**: 2026-09-05  
**决策者**: 乔瑞雪

## 背景

README 已知限制列明 SQLite 的并发写限制；`.env.example` 已留好 PostgreSQL 切换串；CI 与本地均跑 `file:./dev.db`。当前是本机演示、单人使用、数据量为演示库规模（个位数 Case/Intake），SQLite 完全够用。

## 可选方案

1. 参赛阶段即迁移 PostgreSQL
2. 试点启动时迁移（触发条件驱动）
3. 永不迁移

## 决策

采用方案 2：**参赛阶段不动，试点启动时迁**。触发条件 = 出现试点承诺或多用户并发写入的真实需求；触发前不迁移。

迁移时的不可妥协（继承自决策分析，届时逐条验收）：

1. 迁移不得中断「可演示」状态：任意时刻 dev 环境能 `db:push` + `db:seed` + 跑通黄金链路。
2. `db:reset` / seed / 不变量脚本在新库行为等价。
3. 必须有回滚路径（迁移前后可切回，或保留 SQLite 分支能力）。

顺带约定：Case 编号 `count()+1` 并发重号问题（README 已知限制，`apps/web/src/lib/case-number.ts` 注释预留）在迁移时一并改为数据库序列，在此之前的运行态维持现状、不为演示顺手修。

## 后果

- 参赛阶段继续用 SQLite；省下的时间投入真实视觉模型质量验收与比赛材料。
- 已知限制继续成立：并发写场景（多坐席同时确认）未解，对外材料不得声称支持多用户并发。
- 触发条件出现时按上述不可妥协清单执行迁移，并补一条 devlog 记录。
