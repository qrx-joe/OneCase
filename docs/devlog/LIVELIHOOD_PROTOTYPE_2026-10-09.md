# 民生服务最小原型（2026-10-09）

## 改动与目的

OneCase 增加 `/services` 民生服务跟进页，围绕就业帮扶、老年助餐和探访记录服务对象、本人意愿、内部负责人、下一步行动与时间，以及转介和服务反馈。

当前通过人工创建服务事项，或从已确认事项详情的“服务跟进”入口启动。已有 AI 来件分析/人工确认路径保留；本轮没有扩展 AI 提取契约、提示词或真实模型评估，也没有把合成样本写入 Mock 识别结果。

## 已实现的边界

- 未知对象/本人意愿可以保存计划；未核实前不能记录日常转介发出、实际提供服务或确认结果。
- 已核实对象不可改绑；取消“已核实”标记仍保留历史对象锁定。类型不可改绑，目标/意愿改变后原结果失效。
- 个人服务退出原公共事项的文字/地点查重池；旧确认接口拒绝直接关联个人服务，避免绕过对象核实。已有物业分类的事项不能直接改为个人服务，要另建需求。
- 转介发出与接收分开记录；退回、失联和继续跟进需要下一次联系时间。预约/推荐不作为成功结果。
- 服务提供后需反馈依据和人工确认才能记为本次完成；旧状态 API 同样执行该检查。探访确认结果须保留下一次联系时间。
- 已收尾记录保留历史；新周期新建事项并关联同对象、同类型的已完成事项，不继承结果或本人意愿确认。
- 创建使用幂等键；计划/进展与现有状态变更共用 Case.version，条件写入与处理记录在同一 SQLite 事务提交，失败不发布结果。

## 结构影响

页面 → 新服务 API → `service-case-service.ts` → 现有 Case / Intake / CaseSource / CaseAction。

`service-record.ts` 定义版本化快照、输入校验、进展与收尾规则。服务步骤不替代 Case 状态机，仍复用 domain 的迁移矩阵。快照保存在 CaseAction.toValue，并为每次人工操作保留可读 note；读取最新快照，历史不覆盖。

改动旧路径仅限导航/详情入口、个人服务候选隔离、确认关联守卫与收尾检查。数据库 schema、生产依赖、原分类字典、seed、AI 提取层均未修改。采用现有存储便于回滚和验证；大量查询、报表、复杂对象关系需要后续专门字段设计，不能把本方案称为成熟个案管理架构。

## 独立演示

```powershell
pnpm --filter @onecase/web dev:livelihood
```

入口：[本地民生服务页](http://localhost:3200/services)。登录沿用演示账号，见仓库 README。使用仓库 `tmp/livelihood-demo.db` 和独立构建目录；首次初始化标准合成 seed，后续启动保留原型数据，不复制或清空 dev.db / e2e-demo.db。强制 Mock、清空真实模型 Key、只监听 127.0.0.1；合成服务案例由页面按钮预填，需人确认后保存。

就业演示：选择就业合成案例 → 核实对象/意愿、填写已核实去向 → 创建 → 记录发出/接收 → 记录提供指导 → 记录居民反馈 → 按现有状态机完成本次事项。

养老演示：选择助餐或探访合成案例 → 分别核实本人意愿与安排 → 创建 → 记录实际服务和反馈 → 探访填写后续时间 → 完成本次事项 → 开启新周期。只联系不上时选择失联，保留未知结果和再联系时间。

## 未覆盖与下一步

1. 就业/养老的真实模型提取质量、多对象自动拆分未评估；入口支持人工分开建服务计划，不宣称 AI 已覆盖民生场景。
2. 个人服务的新来件身份核实与 CaseSource 关联尚未开放，后续只能人工记进展；旧 Review 关联出口会拒绝个人服务目标。
3. 服务对象是人工引用编号，没有居民主档、家庭授权关系、资格审批或真实服务资源接口。本人意愿来自工作人员确认，不是有效授权文件的替代。
4. 延续原型的演示登录边界，没有后端生产鉴权；仅使用合成资料。紧急风险提示不代表已发起救援，工具不发送任何外部消息。
5. 先请一线工作人员核对职责、实际收尾条件及重复录入负担。再决定分类、提取契约、来源关联和持久化字段的下一轮范围。
