# 图片输入与验证记录

2026-08-31：新建居民信息页已接通单张图片输入。支持选择文件、拖拽和粘贴，允许 JPG / PNG / WebP，最大 10 MB；图片可单独提交，也可带补充说明。

## 数据流程

- 选择图片时只在浏览器预览；点击“AI 整理为事项”后才提交。
- `POST /api/intakes` 继续支持原有文字 JSON 请求。图片使用 multipart：`image` 为文件，`metadata` 为 JSON 字符串，包含 `rawText`、`sourceType: "image"`、`organizationId` 和可选 `idempotencyKey`。JSON 包装避免 multipart 改写原文换行。
- 服务端限制请求实际大小、图片类型和文件头。Intake 与 Attachment 在同一事务内保存，重放提交会比较原文和图片内容。
- 本地 MVP 将图片作为 data URL 存入现有 Attachment 表，不写 public 目录、不创建公开文件链接；无需数据库迁移。此方式只适合小规模本地演示，尚无生产级认证、访问控制和留存策略。
- 分析时读取已保存图片，以 OpenAI 兼容的 `image_url` 消息发送给 Qwen/OpenAI/StepFun。图片和文字均按不可信输入处理，模型输出仍须通过原有结构校验。
- 失败后复用已保存的 Intake；刷新可恢复原图。AI 草稿确认页和手动创建页均可对照原图，最终仍由人工确认是否建档。
- 语音入口禁用并显示“暂未支持”，未实现录音或 ASR。

## 模型配置边界

`GET /api/intakes/capabilities` 只检查本地 Provider 装配，不发送模型请求、不返回密钥。真实 Provider 已配置不代表所选模型一定支持视觉，仍需使用支持图片的模型进行验收。

2026-08-31 检查时运行模式为 `mock / mock-v1`。2026-09-05 当前本地服务的能力接口返回 `stepfun / step-1o-turbo-vision`，一条带单张合成图片的 Intake 已从上传进入分析并到达 Review：Intake 状态为 `ANALYZED`，对应 Analysis 为 `COMPLETED`，审计记录为 `stepfun / step-1o-turbo-vision`、`latencyMs=3449`，并持久化了 1 条 Issue。这证明当前配置下的单张图片正常链路已经贯通，不证明识别内容准确、稳定或适用于代表性社区图片。

能力接口当前用“非 Mock Provider”近似表示 `imageProviderConfigured`，并不会识别具体模型是否支持视觉。因此它只能作为装配检查，不能单独作为图片能力验收。Mock 遇到图片会明确失败，不会返回固定演示结果冒充图片识别。启用真实识别需要在本地服务的环境变量中设置 `AI_PROVIDER=qwen`、`openai` 或 `stepfun`，以及对应的 API Key 和支持视觉的模型名；更改后重启服务。不要将密钥写进代码或提交到仓库。

本轮闭环审查没有新增外部模型调用或上传私人截图，也没有运行完整 Playwright E2E。当前 E2E 配置会复用 `localhost:3000` 的既有服务，而每个 spec 会重置数据库；在真实 StepFun 服务运行时直接执行，既可能清空演示数据，也可能产生真实调用，所以必须先隔离数据库并强制 Mock。拖拽和粘贴处理已实现，但上述浏览器验收使用的是文件选择器。

仍未闭环的代码风险包括：分析结果最终写库失败时 Intake 可能停留在 `ANALYZING`，直到超时恢复；能力接口可能把纯文本模型误报为可处理图片；Review 页面未显示实际 provider/model；StepFun 尚缺 HTTP 失败到数据库审计的专属端到端覆盖。详见 [StepFun 接入闭环审查](../review/StepFun接入闭环审查-2026-09-05.md)。
